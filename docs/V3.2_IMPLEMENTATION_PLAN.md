# Link Nest v3.2 Implementation Plan

Created: 2026-10-05 | Branch: `v3.2` | Status: Save reasons, selective Markdown exports, clipboard capture, reading positions, related-link suggestions, and review history implemented; Undo and offline library access remain planned

Context: [Product](PRODUCT.md), [Brand](BRAND.md), [Shipped features](FEATURES.md), [API](API.md), [Future plan](FUTURE_PLAN.md).

## 1. Outcome and scope

Implement all eight requested features while keeping Link Nest a private, lightweight knowledge inbox:

1. Undo the last archive, status change, or bulk action.
2. Save and resume article reading position through the browser extension.
3. Capture an optional reason for saving a link and show it during review.
4. Suggest related links for the user to connect manually.
5. Show a per-link history of review decisions and note changes.
6. Browse downloaded link titles and notes offline.
7. Export selected links or the current filtered topic as Markdown.
8. Save a copied URL through an explicit extension clipboard action.

Save reasons, selective Markdown exports, clipboard capture, reading positions, related-link suggestions, and review history
are implemented in source. Existing databases need the query-only
[db-changes.sql](db-changes.sql) applied manually before deployment. No SQL has
been executed. Other sections specify future implementation.

### Proposed product defaults

- Preserve Node.js, MySQL, vanilla JavaScript, existing design tokens, and the current single-user model.
- No new runtime dependencies are expected. Reuse `mysql2`, existing serializers, native browser APIs, and current URL validation.
- Reading position is explicitly saved and resumed from the extension popup. Continuous tracking is a later enhancement.
- Offline library access is an opt-in, read-only download of metadata and notes. Existing offline capture remains available.
- Use a separate optional `saveReason` field. Reusing notes is simpler, but would mix capture intent with later takeaways and note-based revisit measurement.
- Undo covers successful archive/status operations, including a takeaway entered as part of marking useful. Standalone note editing, hard delete, imports, and relationship changes do not receive undo in this release.
- Related suggestions use deterministic tag/title matching. No AI service or persistent recommendation score.
- Proposed limits below are implementation defaults, to validate against representative library sizes before release.

## 4. Shared backend foundation

Implemented foundation: `withTransaction()` and durable `link_events` only.
Version 3 exports request repeatable-read isolation for a consistent snapshot.
The revision/action/request-ID/undo-snapshot storage below remains planned for
Undo; it is intentionally absent from this history release.

### Transactions and compatibility

- Add `withTransaction(work)` in `lib/db.js`: acquire one connection, begin, commit or roll back, always release. Every participating query must use that connection.
- Keep the existing `query()` contract for unrelated callers. Pass a transaction query function to the small set of write helpers that need it.
- Add an internal monotonic `revision` to links. Increment it for every link mutation, including open tracking, restore, note merge, bulk updates, and review completion.
- Lock affected links in sorted ID order with `SELECT ... FOR UPDATE`; validate all members before applying a bulk action.
- Use server-generated action IDs and an optional client request ID for new action requests. Scope request-ID uniqueness to the authenticated user, and reject reuse with a different payload.
- Store the original result for retries. A repeated committed request returns that result without another mutation or history event.
- Preserve existing routes and response fields. Add optional action metadata; support new routes under both `/api/` and `/api/v1/`.
- Place named routes before generic `/:id` handling. Existing authentication and token scope rules apply to every new endpoint.

### Proposed additive storage

| Storage | Fields and purpose |
| --- | --- |
| `links.revision` | Unsigned integer, default 0; internal conflict detection, not client-writable |
| `links.save_reason` | Plain text, default empty, maximum 500 characters |
| `link_actions` | ID, actor user ID, optional request ID, request fingerprint, kind, created time, undo expiry, undone time, retry result |
| `link_action_items` | Action ID + link ID, changed-field before/after snapshots, revision after commit; temporary undo data |
| `link_events` | Event ID, link ID, action ID, actor, type, occurred time, compact metadata; durable timeline |
| `links.reading_position` | Implemented nullable JSON: canonical URL, ratio, viewport offset, bounded heading text, scroll distance, server save time |

- Index events by `(link_id, occurred_at, id)`, actions by actor/time and expiry, and enforce action-item uniqueness.
- History stores event summaries, not permanent copies of old note text. Temporary snapshots may contain a takeaway only when necessary to reverse a compound useful action.
- Expire undo snapshots and retry payloads after 24 hours through a bounded maintenance task; expiry is enforced at request time regardless of cleanup timing. Keep compact timeline events until permanent deletion.
- Hard-deleting a link removes its positions and history and invalidates any pending undo that includes it. Soft archive retains history.
- Existing rows get defaults, without fabricated historical events. Label the timeline with the date recording began.
- Put schema changes as queries only in `docs/db-changes.sql`, as requested.
  Update the fresh-install schema; do not add migration files or execute SQL.

## 5. Feature: Undo last action

### User experience

- After archive or status change, show an actionable toast: `Link archived. Undo` or `12 links updated. Undo`.
- Keep the toast visible for 15 seconds, pausing dismissal while focused or hovered. Provide the latest action in a small Recent action control for the server's 10-minute undo window.
- Keep one latest undoable action per browser tab, with no redo stack. A failed or no-op request must not replace it.
- After undo, refresh affected rows, review progress, selection, badges, and weekly statistics. An undone review decision returns to its review session when still eligible.
- Offline or expired undo shows a clear message and never claims restoration. Conflict messages explain that a link changed after the original action.

### Server behavior

- Add `POST /api/links/actions` for explicit single/bulk operations: `{ requestId, kind, ids, status?, takeaway? }`, where kind is `archive` or `status`.
- Validate 1-200 distinct IDs; `takeaway` is allowed only for one link being marked useful and uses the existing 10,000-character combined-note limit.
- Return changed entries/count and `{ action: { id, undoExpiresAt } }`. Record only actual changes; reject invalid bulk members atomically rather than silently skipping them.
- Capture server-side before/after values for affected fields, including status, deletion, pin state, notes when supplied, and review milestones.
- Add `POST /api/actions/:id/undo`. Verify actor, expiry, action state, and every current revision under lock before restoring anything.
- Restore only action-owned fields. Set a new `updatedAt`, increment revisions, append an undo event, and mark the action undone in the same transaction.
- A repeated undo returns the recorded successful result. A conflicting member causes `409` and zero restores; expired actions return `410`.
- Conservative conflict rule: any intervening link mutation, even open tracking, invalidates undo. This avoids overwriting subsequent work and is documented in the UI error.
- Never call ordinary restore to emulate undo; never trust client-provided previous records. Undo itself must not set new meaningful-review milestones.
- Existing API writes still work and record history. Web archive/status controls switch to the new action endpoint; legacy bulk behavior remains compatible.

### Files and verification

- Backend: `lib/db.js`, `lib/links.js`, new focused `lib/link-actions.js`, action route module, and router registration.
- Frontend: `public/js/shared.js`, `browse.js`, `home.js`, `archive.js`, and editor status handling; a focused undo UI script if needed.
- Tests: exact pinned/status/archive restoration; useful plus takeaway; 24-hour milestone boundary; whole-batch rollback; two-tab conflict; duplicate request/undo; expiry; unauthorized/read-token denial; no-op behavior.

## 6. Feature: Review history

Status: implemented on 2026-10-05. Existing databases require only the new
`CREATE TABLE IF NOT EXISTS link_events` query from [db-changes.sql](db-changes.sql)
when earlier columns already exist. No SQL was executed and no migration was added.

The editor uses a collapsed, lazy-loaded history section, 20 newest events per
page, inline retry, and Bangkok timestamps. Both API prefixes support authenticated
read tokens and validated timestamp/UUID cursors. Domain writes lock rows and
commit each event with its change, including legacy routes and extension writes.
Compound operations create one compact summary. No-op edits, repeated archive or
restore, opening, and position saves do not create events. Detail edits and imports
have explicit Details updated/Imported labels. Existing links receive no backfill.

Version 3 embeds history on each link in the complete backup. Preview and existing
100-link import batching preserve it. Validated events restore atomically only
with newly inserted links; duplicate links skip their history. IDs and timestamps
survive, current importer supplies actor attribution, and event conflicts roll
back the link as invalid. Note/reason versions and incoming actors are rejected.
There is no fixed event-count cap; request/file size limits remain applicable.
Old arrays and version 2 remain accepted. Request-ID deduplication and Action undone
events await Undo; merge-note retries retain their existing append behavior.
Automated transactions, domain, backup, pagination, authorization, and DOM tests
pass. Real-browser and disposable-MySQL smoke checks remain pending.

### User experience and events

- Add a collapsed History section to the editor, newest first, 20 events per page with Load more.
- Show clear events: Saved, Imported, Note updated, Marked useful, Status changed, Snoozed, Archived, Restored, Useful review completed, Save reason updated, and Details updated. Action undone arrives with Undo.
- Group a compound action into one readable item; show before/after status where helpful. Render note-change summaries without presenting a version-recovery tool.
- Display timestamps in Asia/Bangkok. Empty state says history starts after the feature was enabled.
- Opening and position saves do not generate review events. Preserve existing meaningful-review and 14-day cohort rules.

### Implementation and tests

- Add `GET /api/links/:id/history?cursor=...&limit=20`, maximum 100; use a validated `(occurredAt, id)` cursor for stable pagination.
- Record events in the same transaction as each domain mutation, including legacy routes, bulk actions, extension writes, merge-note, and useful-review completion.
- Use `req._auth` for actor attribution; do not store raw session or API tokens. A no-op edit produces no event.
- Import records as imported data, without pretending an import was a new review decision. Restore exported history only through validated backup input.
- Add focused `lib/link-history.js` and editor history script; follow existing route and DOM conventions.
- Tests: event coverage across entry points, ordered pagination, atomic rollback, no duplicate retry event, no-op suppression, soft-archive visibility, and permanent-delete cleanup.

## 7. Feature: Why I saved this

## 8. Feature: Selective Markdown export

Status: implemented in source. Browse exports all matching pages or chosen IDs;
review-session exports use remaining visible IDs. Strict scope/filter validation,
exact exported counts, safe tags, and actionable download errors are tested.
No database changes are needed for this feature.

### Scope and behavior

- Add Export selected to Browse bulk actions and Export current view to the library controls.
- Selection exports exactly the chosen IDs, up to 200. Current view exports all matching links, not just the loaded page; cap at 5,000 and ask for narrower filters above that.
- Include title, URL, status, saved date, tags, save reason, and notes. Reuse the existing Markdown escaping/URL serializer.
- Export the actual review/useful-review queue when that view is active; reuse its query builder rather than approximating its rules with status filters.
- Keep existing full-library JSON/CSV/Markdown downloads available. Label the requested scope and count before download.

### API and tests

- Extend `GET /api/links/export.md` with explicit `scope=selected&ids=...` or `scope=filtered` plus existing validated list/view filters.
- With no scope, preserve current full-export behavior. Reject unknown scopes, mixed selection/filter input, excess IDs, and malformed filters.
- For selected export, resolve all IDs before responding; missing IDs return an error rather than a silently incomplete file. Respect deliberate archive view selection.
- Reuse server-side list validation and ordering, omit pagination for filtered export, and use parameterized queries. Return a private, no-store attachment. Review-session UI exports visible IDs through selected scope instead of querying a refilled queue.
- Use GET so existing read-scoped API tokens can export without changing blanket POST authorization rules.
- Tests: exact selected IDs, filters beyond first page, YouTube/review views, empty export, limits, archive scope, hostile Markdown, stable order, and legacy full exports.

## 9. Feature: Save from clipboard

Status: implemented in extension 1.1.0 on 2026-10-05. No database changes or
dependencies were added. Automated popup tests pass; real Chromium permission
and popup smoke tests remain pending because browser automation was unavailable.

- Add an explicit Paste and save button in the extension popup. Read the clipboard only from that user action.
- Accept one trimmed absolute HTTP/HTTPS URL; reject credentials, unsupported protocols, empty text, and multiple URLs. Keep ordinary paste into the URL field available.
- Clear the active tab's title before capturing a different clipboard URL. Fetch metadata using the existing protected metadata endpoint, with URL fallback if unavailable.
- Reuse the popup's capture, tags, notes, reason, duplicate, and error paths. Disable the action during a request and restore controls on every failure.
- Try browser-supported user-gesture clipboard access first. On access failure,
  change the action to Allow clipboard and save. Its next explicit click requests
  optional `clipboardRead` permission before any await. Denial leaves manual paste usable.
- Accept up to 2,048 URL characters. Bound title metadata lookup to five seconds;
  failures fall back to the copied URL without inheriting the active tab's title.
- Do not read clipboard on popup load, store clipboard history, or send clipboard text anywhere other than the configured Link Nest capture flow.
- Files: `extension/popup.html`, `popup.js`, and `manifest.json` if optional permission is needed.
- Tests: gesture-only access, permission denial, empty/multiline/unsafe URLs, no stale tab title, duplicate response, missing configuration, and network retry. Verify in actual supported Chromium browsers.

## 10. Feature: Reading position

Status: implemented in extension 1.2.0 on 2026-10-05, with backend, router-auth,
injected-page, and popup tests. Existing databases need the new nullable JSON
column from query-only `db-changes.sql`. No SQL was executed. Real Chromium and
disposable-MySQL smoke checks remain pending; automated persistence tests use mocks.

Storage uses one JSON field on the link instead of a separate table. One
conditional UPDATE guards active-link URL identity, URL edits clear it in the
same write, and hard deletion naturally removes it. JSON backups remain version
2 with an additive embedded `readingPosition`; no dependent-record remapping is needed.

### User flow

- On a saved article, extension popup shows Save position and Resume reading. An unsaved page offers Save link first.
- Save a scroll ratio between 0 and 1 and a bounded nearby heading anchor plus viewport offset. Avoid capturing article bodies or form text.
- Resume locates the heading when possible and falls back to scroll ratio against the current scrollable height. A changed page shows approximate-position feedback.
- Position is independent of link status: saving or reaching the bottom never marks useful, completes review, or changes review statistics.
- Launch scope: ordinary top-level HTML articles. Browser internal pages, extension stores, PDFs, embedded readers, and virtualized feeds show unsupported feedback.

### API, extension, and tests

- Add authenticated `GET /api/links/lookup?url=...` with binary exact canonical URL lookup; do not substitute fuzzy duplicate matching for identity.
- Add `GET /api/links/:id/reading-position?url=...` and `PUT /api/links/:id/reading-position`.
- Validate finite ratio/offset values, anchor text up to 200 characters, and URL identity against the saved link. Use server time; latest successfully committed explicit save wins across devices.
- Clear position when the link's canonical URL changes, and remove it on hard delete. Include it in complete JSON backups; it is not a review-history event.
- Position saves do not change `updatedAt` or open counts. Validate ratio 0-1,
  offset +/-100,000 pixels, heading text up to 200 characters, and maximum scroll
  distance up to 100,000,000 pixels. See [API.md](API.md) for the exact contract.
- Add `scripting` permission and inject a small isolated-world script only after popup interaction using existing `activeTab`. No automatic all-site scroll listener.
- Keep token and server requests in extension contexts, never in the page. Recheck tab URL before applying a saved position if navigation occurred.
- Basic Resume works on the current article tab after reopening it; do not promise automatic scrolling when opening a link from the web app.
- Tests: top/bottom/zero-height pages, changed layout, missing heading, navigation race, normalization, unsaved/deleted links, invalid payloads, revoked tokens, and real save/reopen/resume flow.

## 11. Feature: Related-link suggestions

Implemented without schema changes or dependencies. Suggestions use persisted
tags and titles, so save editor changes before expecting new matches. The
candidate query prioritizes shared-tag count, then binary ID, before its 200-row
limit. Tags are trimmed and case-sensitive. Blank and URL fallback titles cannot
qualify by title similarity. Results rank by shared tags, title similarity, then
ID and include a plain-text explanation. Both API prefixes support read tokens.
Connect refreshes the canonical related list; request counters discard stale
responses. Retry handles load failures, and keyboard focus survives row updates.
Automated ranking, authorization, DOM safety, races, and manual relationship
regression tests pass. Real-browser and disposable-MySQL checks remain pending.

- Add Suggested connections below existing related links in the editor, up to five results with a reason such as `Shares tags: javascript, testing`.
- Retrieve candidates from active links sharing at least one exact normalized tag or the same host; cap the candidate set at 200 with deterministic ordering.
- Exclude the current link, archived links, and existing relationships. Rank by shared-tag count, then existing Jaro-Winkler title similarity, then ID.
- Require shared tags or title similarity of at least 0.85 before showing a result; same host alone is insufficient. Treat 0.85 as a starting value to verify against representative fixtures.
- Add `GET /api/links/:id/suggestions`; never persist scores, fetch remote pages, or create a relationship automatically.
- Connect uses the existing related-link POST endpoint. Concurrent duplicate connection is handled as already connected. Skip for now hides a suggestion for the current editor session.
- Reuse current related-links UI and backend helpers; add bounded candidate query logic in a focused module if needed.
- Tests: stable ranking, tag/title reasons, exclusions, candidate/result caps, no signals, duplicate connection races, and explicit-confirmation-only writes.

## 12. Feature: Offline library access

### Download contract and interface

- Add Download library for offline use in Settings, showing last successful download, link count, and Clear downloaded library.
- Download active link metadata, tags, reason, and notes. Initial cap: 2,000 most recently updated links and 25 MiB serialized data. Show partial-library status and total count if truncated.
- Add `GET /api/links/offline-snapshot`, returning a bounded consistent snapshot with `links`, `total`, `complete`, `downloadedAt`, and schema version; use private, no-store HTTP headers.
- Read the snapshot under one consistent database transaction. Explicit full replacement on refresh handles remote archive and hard delete without a new tombstone protocol.
- A dedicated Offline library view supports local title/URL/tag/note search and basic filtering. Show cached age and limited scope; do not imply uncached articles can be opened offline.
- Offline library editing and review actions remain disabled. New captures continue through the existing capture queue and retain separate pending/failed states.

### Storage, authentication, and failure behavior

- Upgrade `linknest-offline` through one shared IndexedDB opener used by capture and library modules. Preserve the existing captures store; add library and metadata stores.
- Handle `versionchange` by closing connections and `blocked` by asking stale tabs to reload. Existing capture clients must tolerate the database version upgrade.
- Build each snapshot separately; replace the old library only after validation and one successful transaction. Quota failure or interrupted download leaves the previous snapshot intact.
- Keep API fetches network-only in the service worker. The offline view reads IndexedDB explicitly; do not cache arbitrary authenticated API responses.
- Bind downloaded data to the last verified user identity. Require online login for first setup; offline access is available only on the device where downloading was enabled.
- Explain at opt-in that downloaded notes are stored on this device and remote session expiry cannot revoke them while disconnected.
- On explicit logout, online `401`, or account change: clear library data and protected page caches, reset identity, and notify other tabs. Never fall back to cached data after a known authorization failure.
- Centralize UI logout and cover direct `/logout` navigation through service-worker/page cleanup. Protect against late in-flight downloads repopulating data after logout using a local generation marker.
- Keep unsynced captures separate from library deletion. Bind new captures to identity; quarantine legacy/unowned drafts until the user confirms after login. Do not automatically submit them under another identity.
- Offer optional persistent storage via native browser APIs after opt-in, but tolerate refusal and eviction. Show an empty/download-again state if storage disappears.
- Tests: IndexedDB v1 upgrade without draft loss, old tabs blocking upgrade, offline restart, search, truncation, interrupted refresh, quota/eviction, deleted-link removal, logout through both paths, `401`, cross-tab cleanup, late download race, and account isolation.

## 13. Cross-feature compatibility and release

### Backup and import contract

- Version 3 now includes durable per-link history, save reasons, and embedded
  positions, while accepting legacy arrays and version 2 backups.
- Export links, relationships, positions, and history from one consistent snapshot. Never export sessions, tokens, revisions for restoration, active undo snapshots, or retry credentials.
- Restore links first, then remap dependent records using validated old-to-new IDs. Duplicate/skipped links must have an explicit mapping or dependent data is reported skipped.
- Validate event types, dates, lengths, IDs, and position bounds. Imported event IDs are deduplicated; imports never recreate active undo actions or increment review milestones.
- Test complete restore and partial batch failures, including a repeated restore. If record limits require chunking, report per-section progress and recoverable failures.

### Testing and review gates

1. Record baseline `rtk npm test` results and coverage before code changes. This planning task does not establish a passing baseline.
2. For each non-trivial slice, write and run a failing behavior test, implement, then refactor. Keep tests focused on outcomes rather than source-text patterns.
3. Use existing `node:test` mocks for unit coverage and route tests for authentication, validation, response shape, and errors.
4. Use a disposable MySQL database for migration, transaction, concurrency, rollback, and backup tests. Never point integration tests at production.
5. Target at least 80% line, branch, and function coverage for changed modules and report repository coverage; document uncovered browser paths and verify them through real-browser tests.
6. Check desktop and 390/768/1024 px widths, keyboard-only use, focus restoration, reduced motion, and touch targets.
7. Exercise capture, review, undo, export, extension, and offline journeys together. Verify old browser/API clients still work.
8. Use planner/reviewer subagents for implementation according to project rules; resolve all critical/high findings. Run security review before committing.

### Rollout and rollback

- Back up production and test a restore before schema changes. Confirm deployed MySQL version, indexes, table sizes, and migration privileges.
- Deploy additive schema first, compatible backend second, then web assets/service worker and extension. Bump their versions when behavior ships.
- History requires schema-first deployment of the table before backend and web assets; rollback restores prior code and retains the table. Undo/offline rollout controls remain future work.
- Prefer rolling back application code while leaving additive tables/columns intact. Disable affected UI/API entry points; do not drop history or user data as routine rollback.
- An old application version will not increment revisions: clear/expire all pending undo actions before rollback, and do not reuse them after re-enabling.
- Offline rollback must preserve unsynced captures and keep a compatible IndexedDB opener. Disable the library UI without downgrading the database version.
- Update `API.md`, `FEATURES.md`, `DATA_FLOW.md`, fresh-install SQL, and release notes as slices ship. Keep this plan's completion checklist current.
